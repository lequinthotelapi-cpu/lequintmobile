# ADR-001 — Framework: Flutter

**Estado**: CONFIRMED (DECISION-001)

## Contexto
Se necesita construir una app móvil para iOS y Android que se sienta nativa y esté diseñada específicamente para móvil.

## Problema
Elegir el framework de desarrollo móvil.

## Alternativas evaluadas
- **React Native**: TypeScript, una base de código, ecosistema maduro, Firebase bien soportado.
- **Flutter**: Dart, una base de código, rendimiento nativo, UI altamente personalizable, Firebase bien soportado (FlutterFire).
- **Ionic/Capacitor sobre Angular**: Reutiliza código Angular existente, pero produce WebView, no app nativa real.

## Decisión
**Flutter**

## Justificación
- Una base de código para iOS y Android
- Rendimiento nativo (no WebView)
- UI completamente personalizable — cumple el requisito de "sentirse diseñada para móvil"
- FlutterFire es el SDK oficial de Firebase para Flutter, bien mantenido
- Ionic descartado porque produce experiencia híbrida, no nativa

## Consecuencias
- Lenguaje: Dart (curva de aprendizaje si el equipo no lo conoce)
- No se reutiliza código Angular del sistema web
- Se reutilizan modelos de datos, reglas de negocio y colecciones Firestore

# ADR-002 — Backend: Firebase (reutilización)

**Estado**: CONFIRMED
**Fecha**: Sesión inicial

## Contexto
El sistema web usa Firebase (Auth + Firestore + FCM + Storage). La app móvil necesita acceder a los mismos datos.

## Problema
¿Crear un nuevo backend o reutilizar Firebase?

## Alternativas evaluadas
- **Reutilizar Firebase directamente**: La app accede a Firestore con el mismo usuario Firebase Auth.
- **Crear API REST intermedia**: Capa adicional entre la app y Firebase.

## Decisión
**Reutilizar Firebase directamente**

## Justificación
- Las colecciones Firestore ya existen y tienen la estructura correcta
- Las Firestore Rules ya implementan seguridad por rol
- Firebase Auth ya maneja autenticación y sesiones
- FCM ya está configurado
- No se justifica una capa intermedia para el MVP

## Consecuencias
- La app móvil accede directamente a Firestore con el token del usuario autenticado
- Las Firestore Rules existentes aplican automáticamente
- Cualquier cambio en la estructura de Firestore afecta tanto al sistema web como a la app móvil

# ADR-003 — State Management: Riverpod

**Estado**: CONFIRMED (DECISION-001 implícito — parte del stack Flutter confirmado)
**Fecha**: Sesión inicial

## Contexto
Flutter requiere una solución de gestión de estado para manejar datos reactivos, caché, y estado de UI.

## Problema
Elegir la solución de state management para Flutter.

## Alternativas evaluadas
- **Riverpod**: Compilación segura, sin BuildContext requerido, excelente para streams de Firestore, testeable.
- **BLoC/Cubit**: Más verboso, patrón bien establecido, buena separación de capas.
- **Provider**: Más simple, pero limitaciones con dependencias complejas.
- **GetX**: Todo en uno, pero mezcla responsabilidades.

## Decisión
**Riverpod (flutter_riverpod + riverpod_annotation)**

## Justificación
- Integración natural con streams de Firestore (`StreamProvider`)
- Compilación segura (errores en tiempo de compilación, no runtime)
- No requiere BuildContext para acceder a providers
- Excelente para `FutureProvider` y `StreamProvider` que son el patrón principal con Firebase
- Fácil de testear con `ProviderContainer`

## Consecuencias
- Requiere `riverpod_generator` y `build_runner` para generación de código
- Curva de aprendizaje inicial si el equipo no conoce Riverpod

# ADR-004 — Navegación: GoRouter

**Estado**: CONFIRMED (DECISION-001 implícito — parte del stack Flutter confirmado)
**Fecha**: Sesión inicial

## Contexto
La app tiene múltiples pantallas, navegación condicional por rol, y necesita manejar deep links desde notificaciones push.

## Problema
Elegir la solución de navegación para Flutter.

## Alternativas evaluadas
- **GoRouter**: Declarativo, URL-based, deep linking nativo, mantenido por el equipo de Flutter.
- **Navigator 2.0 manual**: Máximo control, pero muy verboso.
- **Auto Route**: Generación de código, tipado fuerte.

## Decisión
**GoRouter**

## Justificación
- Soporte nativo de deep linking (necesario para notificaciones push)
- Redirección declarativa (para auth guard por rol)
- Mantenido oficialmente por el equipo de Flutter
- Integración simple con ShellRoute para bottom navigation

## Consecuencias
- Las rutas son URL-based, lo que facilita el deep linking desde FCM
- `redirect` en GoRouter maneja la protección de rutas por autenticación y rol

# ADR-005 — Persistencia offline: Firestore nativo

**Estado**: CONFIRMED (DECISION-006)
**Fecha**: Sesión inicial

## Contexto
La app debe funcionar con conectividad limitada o sin conexión.

## Problema
Estrategia de persistencia offline.

## Alternativas evaluadas
- **Firestore offline nativo**: `persistenceEnabled: true` en la configuración de Firestore. Caché automático de lecturas, escrituras encoladas.
- **SQLite local + sincronización manual**: Control total, pero complejidad muy alta.
- **Hive/Isar**: Base de datos local Flutter, requiere lógica de sincronización manual.

## Decisión
**Firestore offline nativo**

## Justificación
- Cero código adicional para el MVP
- Lecturas sirven desde caché automáticamente
- Escrituras se encolan y sincronizan automáticamente al reconectar
- Suficiente para el caso de uso: la mayoría de funcionalidades son de consulta
- Las escrituras críticas (completar tarea, check-in) se sincronizan al reconectar

## Consecuencias
- El caché puede estar desactualizado si no hay conexión
- No hay control granular sobre qué datos se cachean
- Para el MVP esto es aceptable

# ADR-006 — Heartbeat de sesión: AppLifecycleObserver

**Estado**: CONFIRMED (DECISION-006 + ASSUMPTION-005 confirmada)
**Fecha**: Sesión inicial

## Contexto
El sistema web implementa un heartbeat cada 5 minutos con `setInterval` para mantener la sesión activa. En móvil el ciclo de vida es diferente: la app puede ir a background, ser suspendida, o cerrarse.

## Problema
Adaptar el heartbeat de sesión al ciclo de vida de una app Flutter.

## Decisión
**Timer periódico + AppLifecycleObserver**

```dart
// Heartbeat activo solo cuando la app está en foreground
// Se pausa en background (AppLifecycleState.paused)
// Se reanuda en foreground (AppLifecycleState.resumed)
// Se cancela en logout
```

## Justificación
- Evita escrituras innecesarias en Firestore cuando la app está en background
- Respeta el ciclo de vida móvil
- Mantiene compatibilidad con el sistema de sesiones existente

## Consecuencias
- Una sesión móvil puede expirar si la app está en background >15 minutos
- Al volver al foreground, si la sesión expiró, el usuario debe hacer login nuevamente
- Esto es comportamiento aceptable y seguro
